👤 Autoriser un nouveau compte (méthode manuelle)

Cette méthode manuelle reste utile en secours si l'ajout depuis l'appli (bouton "Comptes autorisés & administrateurs") ne fonctionne pas, par exemple en cas d'erreur de permissions Firestore.

Étape 1 — Autoriser l'email dans Firestore (donne l'accès)

  1. Ouvre la console Firebase → Firestore Database → collection authorized_emails.
  2. Clique sur un document déjà existant dans la liste pour voir sa structure exacte (nom du/des champ(s), valeur), puis clique sur "Ajouter un document" et reproduis exactement la même structure.
  3. Comme ID du document, saisis l'adresse email exacte de la personne (ex : prenom.nom@entreprise.com) — l'orthographe doit être identique à celle qu'elle utilisera pour se connecter.
  4. Enregistre.
C'est cette étape qui donne réellement accès aux données. Sans elle, la personne peut recevoir un lien de connexion mais n'aura accès à aucun dossier (accès refusé).
Ouvrir la collection authorized_emails ↗

Étape 2 — Vérifier la connexion dans Firebase Authentication

  1. Demande à la personne d'ouvrir l'application et de saisir son email professionnel sur l'écran de connexion : elle reçoit alors un lien de connexion par email.
  2. Dès son premier clic sur ce lien, son compte apparaît automatiquement dans Firebase → Authentication → Users (aucune création manuelle nécessaire de ton côté).
  3. Tu peux vérifier ici que sa connexion a bien fonctionné, et voir la date de dernière connexion.
Cette étape ne fait qu'enregistrer que la personne s'est connectée — elle ne suffit pas seule à autoriser l'accès : c'est bien l'étape 1 (Firestore) qui l'autorise.
Ouvrir Authentication → Users ↗

👤 Comptes autorisés & administrateurs

Aucun administrateur n'est encore défini pour cette instance ("mode bootstrap") : n'importe quel compte déjà autorisé peut se nommer lui-même premier administrateur ci-dessous. Fais-le en priorité pour sécuriser la gestion des comptes.

Un compte doit être dans cette liste pour pouvoir se connecter et voir des données. Le retirer d'ici bloque immédiatement son accès (et le retire aussi des administrateurs, le cas échéant).

    Les administrateurs sont les seuls à pouvoir gérer les comptes autorisés et les administrateurs depuis cet écran. Un administrateur doit d'abord être un compte autorisé.

              🧭 Créer une nouvelle instance CSSCT

              Chaque CSSCT a sa propre instance complètement séparée (projet Firebase dédié + site Cloudflare dédié) : aucune donnée n'est jamais partagée entre CSSCT. Prévoir environ 45-60 minutes par nouvelle instance une fois la procédure rodée.

              Étape 1 — Projet Firebase

              1. Sur console.firebase.google.com, crée un projet nommé par ex. cssct-<nom-entreprise>.
              2. Authentication → Sign-in method → active Email/Password, puis dans ses paramètres avancés active "Lien de messagerie (connexion sans mot de passe)".
              3. Authentication → Settings → Authorized domains : ajoute le futur domaine Cloudflare (tu peux revenir compléter après l'étape 3).
              4. Firestore Database → Créer une base → région proche (ex. eur3) → mode production.
              5. Paramètres du projet → Général → "Vos applications" → icône </> (Web) → n'active pas Firebase Hosting → copie l'objet firebaseConfig affiché (6 valeurs), il sert à l'étape 2.
              ⚠️ Les règles de sécurité Firestore ne sont pas dans ce dépôt (console uniquement). Avant d'ouvrir l'instance à qui que ce soit, récupère les règles du projet existant et adapte-les au nouveau projet — demande à Claude si besoin d'aide pour les relire.

              Étape 2 — Dépôt Git dédié

              1. Crée un nouveau dépôt GitHub vide, puis duplique le dépôt actuel dedans (clone --bare + push --mirror).
              2. Remplace l'objet firebaseConfig dans tous les fichiers HTML qui le contiennent (recherche apiKey: "AIzaSyACY8fyy8Rd9NyLJ855xsDyknuUMV-pAag").
              3. Adapte l'identité visuelle : nom de l'appli (CS2E · CSSCT / Mon appli CSSCT) dans les titres et manifest.json. Le logo, lui, se change directement depuis Administration > Identité visuelle une fois l'instance en ligne — pas besoin de toucher au code pour ça.
              4. Icônes PWA (manifest.json, apple-touch-icon.png, icon-192.png, icon-512.png) : à remplacer manuellement, pas encore paramétrables depuis l'interface.
              5. Adapte les valeurs par défaut de mail de relance (MAIL_RELANCE_DEFAULTS) et le nom dans wrangler.jsonc.
              6. Commit et push.

              Étape 3 — Site Cloudflare Workers

              1. npx wrangler deploy depuis le nouveau dépôt.
              2. Ajoute l'URL *.workers.dev obtenue (ou ton domaine personnalisé) aux "Authorized domains" Firebase (étape 1.3).

              Étape 4 — Premiers comptes

              1. Ajoute ton email dans authorized_emails (console Firebase du nouveau projet).
              2. Connecte-toi une première fois sur le site déployé.
              3. Va dans Administration > Comptes autorisés & administrateurs : la liste d'administrateurs est vide au départ ("mode bootstrap"), nomme-toi premier administrateur en priorité.
              4. Ajoute ensuite les comptes autorisés suivants et la config du mail de relance, toujours depuis Administration.
              Limite à connaître : le code est aujourd'hui dupliqué à l'identique entre chaque instance (pas de configuration centralisée), donc toute correction ou nouvelle fonctionnalité doit être reportée manuellement sur chaque dépôt.
